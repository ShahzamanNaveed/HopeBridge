# Database conventions

A-02 (2026-10-29) now consumes the existing staff/credential/session/event/assignment/audit models for real authentication. No schema or migration was changed in A-02. [Runtime authentication and transactional consumer contracts](authentication.md) supersedes earlier storage-baseline statements that no login service existed; DB-01 invariant and model definitions below are preserved.

Current implementation: **DB-01 initial shared storage and audit writer are implemented/tested locally**, not full business services. The invariant sections retain approved requirements; the implementation inventory below is the current physical contract.

PostgreSQL is authoritative. Use snake_case table/column names mapped to Prisma camelCase fields, explicit foreign keys and uniqueness constraints, query-driven indexes, and UTC timestamptz timestamps. FIN-010 - DECIDED: HWF selects PKR PostgreSQL NUMERIC(18,2), with Prisma Decimal explicitly mapped to precision 18/scale 2. No JavaScript number monetary arithmetic or binary floats. Monetary APIs use decimal strings; accept at most two fractional digits, reject nonfinite/out-of-range/unsupported precision and float-derived amounts. Direct excess-precision records reject rather than round; use explicit HALF_UP only where calculation genuinely needs rounding. Collections/remittances are positive amounts; adjustments are signed. Aggregates, snapshots, dashboards and exports use the same exact model; no multi-currency/exchange rates. Official KPI/fixtures remain unavailable, not invented here.

## DECIDED financial persistence invariants (design only)

- **FIN-011 - DECIDED:** Preserve locked originals, confirmed remittances, Approved snapshots and adjustment history. Keep original occurrence/recognition attribution separate. Signed outstanding may be negative; deficit/available calculations follow [domain measures](domain-rules.md), with available clamped to zero after active reservations. Audited reconciliation must not rewrite old transactions or auto-generate payments/write-offs; exact external clearing/recovery/period settlement remains PENDING.
- **FIN-012 - DECIDED:** Cancellation request alone never releases funds. Finance approval must atomically recheck Pending remittance, record non-reserving cancellation, release its claim once and append audit. Rejection preserves Pending/reservation. Serialize against confirmation; confirmed cannot cancel, cancelled cannot confirm, failure rolls back all state/reservation/audit effects. Prevent negative/double releases with constraints and transactional protection. Confirmed dispute/settlement and bank-evidence policy remain PENDING.
- **FIN-013 - DECIDED:** Database uniqueness/concurrency protection must permit at most one PendingReview request per original while allowing later requests after decision. References are unique and immutable; preserve each request, decision and audit plus all previous approvals. Transactionally serialize cumulative approval against original plus all Approved deltas, including Approved awaiting recognition; reject corrected value below zero. Recognition of each Approved adjustment is exactly once in the eligible period; Rejected has no effect. This per-original nonnegative limit does not prohibit a FIN-011 branch deficit.

DB-01 now implements the initial names/enums/indexes below; future changes require reviewed migrations and consumer coordination. Business changes, reservation/recognition effects and audit commit together or roll back together.

## AUTH-001 to AUTH-006 persistence requirements (DECIDED; design only)

Staff/credential/session storage is implemented by DB-01; login/reset/CSRF/permission services remain unimplemented.

- **AUTH-001/AUTH-002 - DECIDED:** Staff credential storage is secure password hash only, with authoritative issuance, exact +24h temporary expiry and mandatory-change controls. One-time plaintext is transient to authorized post-commit provisioning/reset response, never persisted/retrievable/reversibly encrypted, logged or audited. Reset transaction replaces hash/controls, revokes all target active sessions and writes sanitized audit; failure rolls back all persistent changes. Revalidate allowed target state and last-admin safeguards.
- **AUTH-003 - DECIDED:** Persist server-managed revocable sessions with issuance/absolute deadline, idle/activity deadline, revocation and restricted-first-login state sufficient to enforce minimum password-change/logout access. Idle 8h maximum, absolute 24h, deny at earliest deadline; authorized refresh must serialize with expiry/revocation and never resurrect/extend absolute time. Logout revokes; password change securely rotates/invalidates.
- **AUTH-004 - DECIDED:** Staff deactivation, immediate session revocation and status/audit effects are consistent and concurrency-safe, including last-active-admin and required lead replacement. Preserve identity/audit; activation never restores old session/expired temporary credential.
- **AUTH-005 - DECIDED:** Opaque identifier cookie is distinct from server-side session authority; never log session IDs or store authentication secrets in browser localStorage. Follow existing PostgreSQL/session/hash design; cookie/CSRF transport controls are in [security](security.md), not a claimed schema.
- **AUTH-006 - DECIDED:** Assignment constraints and replacement transaction/audit must preserve eligible Active-branch leadership and immediately invalidate prior branch access through revocation or equally immediate server checks. Current role/assignment/active status remains authoritative on every protected query. Store configuration/index/locking details remain implementation choices.

## WR-001 to WR-006 report persistence (DECIDED; conceptual only)

DB-01 implements canonical report/revision/recognition/snapshot tables and guards; scheduler, financial calculations and transitions are still application work.

- **WR-001/WR-005 - DECIDED:** Persist canonical just-completed PKT Monday-to-next-Monday branch/week identity for eligible Active/Paused operational branches, including zero activity. Head Office is not operational; FIN-014 ordinary Closed-branch future reports prohibited; legitimate pre-closure recognition container/period PENDING, old reports never deleted. Zero activity creates no fake financial records.
- **WR-002 - DECIDED:** Unique database constraint on canonical branch/week plus transaction/concurrency safeguards make scheduled generation and catch-up idempotent. Recovery finds missing eligible weeks after downtime, creates safely with system audit/observability and never overwrites/reset existing Submitted/Returned/Approved reports. No reliance on unrecoverable memory-only timer; hosting mechanism unselected.
- **WR-003 - DECIDED:** Maintain distinguishable live eligible Draft/Returned calculation and preserved immutable submission revisions (submitter/time/version/source evidence) for each submit/resubmit. Submitted originals locked; Return does not extend edit age. Preserve previous revisions and atomically locked Approved final snapshot; later records/confirmations cannot mutate old snapshots.
- **WR-004 - DECIDED:** Approval transaction checks unresolved issues relevant to branch/report/recognition scope and potential material snapshot effect, separating occurrence week, recognition week and candidate report. Do not include unapproved amounts or blanket-block unrelated requests. Reassess resolved dependencies; multi-period dependency representation/treatment needs explicit implementation-level specification.
- **WR-006 - DECIDED:** Each system/staff transition rechecks state, version/equivalent atomic control, scope and authority; state/new revision or snapshot/audit commit together, rollback together. Serialize incompatible actions; no duplicate successful transitions/recognition and no Approved reopening/manual lock. Recovery actor is system process, not invented staff identity.

## FIN-014 to FIN-018 persistence invariants (DECIDED; no schema implemented)

- **FIN-014 - DECIDED:** Transactional branch-state checks deny new ordinary Closed-branch collections and ordinary future-week generation, retaining original collections/reports/revisions/Approved snapshots and financial/member/audit histories. Closure never reactivates branch or revives staff scope. Legitimate pre-closure obligations require separately audited existing-role authorization; exact post-closure late-entry/Approved-adjustment recognition container/accounting period PENDING, no new table/report type or reopened snapshot inferred.
- **FIN-015 - DECIDED:** WR-004 approval transaction checks current report/version and relevant unresolved adjustment/Late Entry/material dependency state by branch/period/recognition scope. Relevant material effect blocks, unrelated/mere existence does not; no unapproved inclusion or frozen snapshot rewrite. Resolve then reassess under authorized workflow; precise multi-period treatment still specification work.
- **FIN-016 - DECIDED:** Exact cumulative SAME-branch recognized sums automatically offset signed deficit as future eligible collections are recognized, once only in correct period. Preserve confirmed remittances/originals/old snapshots and metadata; no synthetic transfer or shifted dates. Serialize recognition, reservation and confirmation/balance checks; other branches cannot offset. External/manual settlement remains PENDING, not an implemented posting model.
- **FIN-017 - DECIDED:** Remittance has one branch association and branch-level available-balance reservation/confirmation/cancellation audit. No mandatory foreign-key allocation to every individual collection or allocation algorithm. Preserve required amount/date/reference and optional evidence; once-only confirmations/releases and deficit-aware checks protected transactionally.
- **FIN-018 - DECIDED:** Persist nonempty adjustment reason with actor/original/signed proposal/decision/audit; attachment relationship optional, never substitute for reason/financial checks. Remittance evidence remains optional. Type/size/access/safe-storage controls required for uploads; provider/technical limits not finalized. These conceptual invariants prescribe no new finalized table/field names.

## Integration ownership and transaction boundaries (documentation freeze baseline)

DB-01 implements the initial shared business schema and additive migrations; FoundationMarker and its migration remain unchanged. [Module ownership](architecture.md) governs repositories and transaction-capable service ports; physical tables/column names remain to be reviewed by one accountable schema owner. Auth owns credentials/sessions, users staff state/roles, branches branch/city/code/current lead, applications intake/decisions, members member/Volunteer ID/teams/transfers, collections financial originals/adjustments/recognition/remittances, reports canonical periods/revisions/snapshots, content bilingual CMS and audit the shared append-only writer. Dashboard reads projections only.

### Identity and uniqueness contract

- Staff internal identity is distinct from a member's immutable internal key and permanent city-based Volunteer ID; ordinary members have no staff account.
- Branch internal ID is distinct from immutable city-based display code; application internal ID differs from public application reference. IDs, not names/cities/addresses/client parameters, establish authorized relationships.
- City-scoped branch-code and Volunteer-ID sequences allocate concurrency-safely with database uniqueness; no MAX(id) + 1, no reuse. Same-city branches share member sequence; selected branch's authoritative current city supplies first member prefix; transfer retains it.
- One canonical weekly report per operational branch/PKT week; unique initial accepted-application/member linkage, exactly one member on first acceptance. Reacceptance uses retained member/link/ID; no second allocation. Initial sequence effects and linkage participate in acceptance transaction; do not promise gapless counters.
- Enforce single staff role, one current branch per Branch Lead/at most one assigned active lead per branch and appropriate referential/uniqueness checks in database plus service validation. Exact constraints/index/isolation design remains technical schema work, not missing business approval.

### SQL guards, exact data and integration obligations

- PostgreSQL enforces valid enums/foreign keys, globally unique immutable branch/member IDs, one permanent member per application, one current branch per lead/current lead per branch, one canonical branch/week report, one PendingReview adjustment and one Pending cancellation per source, exactly-once original/adjustment recognition and one reservation per remittance. City sequences allocate by atomic INSERT ON CONFLICT UPDATE, never MAX(id)+1; formatting/padding/overflow governance remains a reviewed domain responsibility.
- Deferred constraints allow atomic lead replacement/activation, Accepted/member linkage, accepted-reversal member inactivation, assignment endings, remittance/reservation settlement, report approval/frozen revision and CMS retirement/pointer clearing. They do not implement application controllers, authorization, accounting or automatic audit for arbitrary SQL writes; service coordinators MUST write required decision/history/audit in the same transaction.
- Partial contact indexes plus sorted advisory locks serialize eligible Pending/Active cross-table email OR phone conflicts while allowing Declined/Inactive history and legitimate original-member self-links. Branch and member eligibility is checked for intake/initial member association. No global lifetime contact uniqueness or identity-proof claim.
- Original collection created_at is server-set and immutable; occurrence-derived PKT week and strict 168-hour/report-state/snapshot lock guards protect direct edits. Closed branches reject ordinary entries/reports. Recognition validates source/report branch, period and Approved adjustment eligibility. Cumulative Approved corrected source amount cannot be negative; this is NOT the branch signed-outstanding engine.
- ReportRevision/ReportLine/ReportApproval/transition/audit/decision history is immutable. Capture lines in the SAME transaction as revision creation; SQL verifies same-report source evidence and creation transaction. ReportApproval links its own report/revision; Approved report locks permanently. Services must still enforce material dependency/role/version and aggregation invariants, capture immutable revisions on every submit/resubmit and compute scoped figures correctly.
- NUMERIC(18,2)/Prisma.Decimal on every monetary field; finite-value and applicable positive/nonnegative checks. **PostgreSQL typemods round excess scale before CHECKs**: consumers MUST use infrastructure/db/money-input.ts databaseMoney(raw) on canonical decimal strings before ORM writes. It rejects JS numbers, NaN/Infinity, exponents, excess precision/scale and noncanonical input. No floating-point accounting or claim that arbitrary raw SQL rejects excess fractional digits. Calculated amounts still require FIN-010 approved Decimal/rounding policy in B's engine.
- All instants are timestamptz(3); remittance transferDate is a date. Report boundaries use Asia/Karachi local Monday; collection edit age is elapsed 168 hours, independent of reporting week. CMS Event instants are unambiguous; Past is computed at server now >= endsAt by future B read services, not a manual publication state.
- CMS enforces same-item published pointers, required bilingual title/body, Program summaries, Event location/end > start and immutable published revisions; optional images do not block. sanitizedAt/MediaAsset.validatedAt record future service validation, NOT a sanitizer or proof the file bytes are safe. B must implement actual rich-text/image validation, private preview/public projection/cache behavior and transactional audit. Fixed page slugs cannot remove routes; no CMS restore policy is invented.
- Audit INSERT API is appendAudit(tx, input) in modules/audit/audit.service.ts. Use the caller's interactive Prisma transaction; root clients rejected via excluded connection capability. Validated STAFF id or SYSTEM name, established domain/action/entity/optional branch and optional object before/after/metadata. Conservative recursive safe-field allowlist redacts contacts/names/notes/secrets/unknown fields, bounds depth/strings and returns only persisted id/createdAt. Failure propagates so caller business changes roll back. SQL rejects audit UPDATE/DELETE/TRUNCATE. Privileged PostgreSQL owners can alter DDL; production runtime least-privilege/retention operations remain separate hardening, not application permission grants.
