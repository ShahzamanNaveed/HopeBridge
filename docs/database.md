# Database conventions

PostgreSQL is authoritative. Use snake_case table/column names mapped to Prisma camelCase fields, explicit foreign keys and uniqueness constraints, query-driven indexes, and UTC timestamptz timestamps. FIN-010 - DECIDED: HWF selects PKR PostgreSQL NUMERIC(18,2), with Prisma Decimal explicitly mapped to precision 18/scale 2. No JavaScript number monetary arithmetic or binary floats. Monetary APIs use decimal strings; accept at most two fractional digits, reject nonfinite/out-of-range/unsupported precision and float-derived amounts. Direct excess-precision records reject rather than round; use explicit HALF_UP only where calculation genuinely needs rounding. Collections/remittances are positive amounts; adjustments are signed. Aggregates, snapshots, dashboards and exports use the same exact model; no multi-currency/exchange rates. Official KPI/fixtures remain unavailable, not invented here.

## DECIDED financial persistence invariants (design only)

- **FIN-011 - DECIDED:** Preserve locked originals, confirmed remittances, Approved snapshots and adjustment history. Keep original occurrence/recognition attribution separate. Signed outstanding may be negative; deficit/available calculations follow [domain measures](domain-rules.md), with available clamped to zero after active reservations. Audited reconciliation must not rewrite old transactions or auto-generate payments/write-offs; exact external clearing/recovery/period settlement remains PENDING.
- **FIN-012 - DECIDED:** Cancellation request alone never releases funds. Finance approval must atomically recheck Pending remittance, record non-reserving cancellation, release its claim once and append audit. Rejection preserves Pending/reservation. Serialize against confirmation; confirmed cannot cancel, cancelled cannot confirm, failure rolls back all state/reservation/audit effects. Prevent negative/double releases with constraints and transactional protection. Confirmed dispute/settlement and bank-evidence policy remain PENDING.
- **FIN-013 - DECIDED:** Database uniqueness/concurrency protection must permit at most one PendingReview request per original while allowing later requests after decision. References are unique and immutable; preserve each request, decision and audit plus all previous approvals. Transactionally serialize cumulative approval against original plus all Approved deltas, including Approved awaiting recognition; reject corrected value below zero. Recognition of each Approved adjustment is exactly once in the eligible period; Rejected has no effect. This per-original nonnegative limit does not prohibit a FIN-011 branch deficit.

Table/field names, status vocabulary and precise locking/index design remain implementation choices, not finalized schemas. Business changes, reservation/recognition effects and audit commit together or roll back together.

## Migration conventions

Commit migrations; use npm run db:migrate for reviewed development migrations and npm run db:deploy in CI/production. Generate the Prisma client with npm run db:generate after schema changes. Seed is idempotent and creates only an infrastructure marker, not users or invented financial data. Production backups and restore validation must precede business rollout.

Finalize domain relationships, report snapshots, audit immutability and transactional boundaries before implementing business modules. Never run reset or destructive migrations against a shared database without explicit approval.

## AUTH-001 to AUTH-006 persistence requirements (DECIDED; design only)

No staff/session Prisma models are implemented. These invariants do not prescribe finalized table/field names.

- **AUTH-001/AUTH-002 - DECIDED:** Staff credential storage is secure password hash only, with authoritative issuance, exact +24h temporary expiry and mandatory-change controls. One-time plaintext is transient to authorized post-commit provisioning/reset response, never persisted/retrievable/reversibly encrypted, logged or audited. Reset transaction replaces hash/controls, revokes all target active sessions and writes sanitized audit; failure rolls back all persistent changes. Revalidate allowed target state and last-admin safeguards.
- **AUTH-003 - DECIDED:** Persist server-managed revocable sessions with issuance/absolute deadline, idle/activity deadline, revocation and restricted-first-login state sufficient to enforce minimum password-change/logout access. Idle 8h maximum, absolute 24h, deny at earliest deadline; authorized refresh must serialize with expiry/revocation and never resurrect/extend absolute time. Logout revokes; password change securely rotates/invalidates.
- **AUTH-004 - DECIDED:** Staff deactivation, immediate session revocation and status/audit effects are consistent and concurrency-safe, including last-active-admin and required lead replacement. Preserve identity/audit; activation never restores old session/expired temporary credential.
- **AUTH-005 - DECIDED:** Opaque identifier cookie is distinct from server-side session authority; never log session IDs or store authentication secrets in browser localStorage. Follow existing PostgreSQL/session/hash design; cookie/CSRF transport controls are in [security](security.md), not a claimed schema.
- **AUTH-006 - DECIDED:** Assignment constraints and replacement transaction/audit must preserve eligible Active-branch leadership and immediately invalidate prior branch access through revocation or equally immediate server checks. Current role/assignment/active status remains authoritative on every protected query. Store configuration/index/locking details remain implementation choices.

## Integration ownership and transaction boundaries (documentation freeze baseline)

No business Prisma schema/migration is created: current schema defines only FoundationMarker. [Module ownership](architecture.md) governs repositories and transaction-capable service ports; physical tables/column names remain to be reviewed by one accountable schema owner. Auth owns credentials/sessions, users staff state/roles, branches branch/city/code/current lead, applications intake/decisions, members member/Volunteer ID/teams/transfers, collections financial originals/adjustments/recognition/remittances, reports canonical periods/revisions/snapshots, content bilingual CMS and audit the shared append-only writer. Dashboard reads projections only.

### Identity and uniqueness contract

- Staff internal identity is distinct from a member's immutable internal key and permanent city-based Volunteer ID; ordinary members have no staff account.
- Branch internal ID is distinct from immutable city-based display code; application internal ID differs from public application reference. IDs, not names/cities/addresses/client parameters, establish authorized relationships.
- City-scoped branch-code and Volunteer-ID sequences allocate concurrency-safely with database uniqueness; no MAX(id) + 1, no reuse. Same-city branches share member sequence; selected branch's authoritative current city supplies first member prefix; transfer retains it.
- One canonical weekly report per operational branch/PKT week; unique initial accepted-application/member linkage, exactly one member on first acceptance. Reacceptance uses retained member/link/ID; no second allocation. Initial sequence effects and linkage participate in acceptance transaction; do not promise gapless counters.
- Enforce single staff role, one current branch per Branch Lead/at most one assigned active lead per branch and appropriate referential/uniqueness checks in database plus service validation. Exact constraints/index/isolation design remains technical schema work, not missing business approval.

| Branch Lead assignment/replacement           | Eligibility/one-branch checks, related permitted staff changes, old/current assignment, immediate stale-access invalidation and old/new audit; rollback retains prior access                                                       |

One coordinator opens the transaction and supplies the same capability to participating module ports and audit writer. No cross-module repository imports, nested independent commit or post-commit audit patch. Revalidate at mutation time and use concurrency-safe constraints/locks/version checks so failed operations leave no partial state. HR decision email is post-commit; delivery failure cannot roll back it. External cache/publication coordination must meet approved visibility requirements; exact mechanism is a technical design review, not relaxed consistency.

All financial storage/aggregation/snapshots use PKR NUMERIC(18,2)/Prisma Decimal, decimal-string transport, no JS float arithmetic. Keep actual occurrence time, server creation time/edit cutoff and recognition/report period distinct. FIN-010 to FIN-018 canonical branch outstanding/deficit/reservation semantics and immutable Approved history apply unchanged. Backend derives current role/branch scope; scoped repositories cannot trust caller branch IDs to expand access. Export reads preserve the same effective report revision/snapshot and audited selection without mutating financial data. No physical ERD or business data is asserted.
