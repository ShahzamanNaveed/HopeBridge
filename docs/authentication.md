## Local use and initial administrator

Run `npm run dev`, then open <http://127.0.0.1:5173/staff/login>. Express runs on port 3000; Vite proxies same-origin API requests. PostgreSQL must be available using the existing ignored root `.env`.

In an interactive terminal, from the repository root:

```powershell
npm.cmd run auth:bootstrap -w @shiplens/backend -- 'your-authorized-email@example.org' 'Super Admin'
```

The command refuses production, remote/unknown database targets, redirected output and noninteractive terminals. It only permits local `hopebridge_dev`. It creates the first Super Admin if none exists, using a transaction/advisory lock; repeated execution changes nothing and discloses nothing. It does not reset an existing administrator. A generated 32-character temporary password appears once in that terminal after commit, expires exactly 24 hours after database issuance, and requires first-login replacement. Capture it privately; never copy it to tracked files, tickets or logs. There is no bootstrap/signup/recovery HTTP endpoint or default administrator password.

For this session, the user explicitly selected the initial local administrator and approved a separate visible terminal for the private handoff. Database verification found one Super Admin and one mandatory-change temporary credential. No actual email or credential is recorded in this document. The administrator's personal first-login change remains theirs to perform; the same full flow was executed with synthetic accounts in disposable databases.

## HTTP contract

All routes below use `/api/v1/auth`, existing `{ data: ... }` / safe `{ error: { code, message, requestId } }` envelopes and `Cache-Control: no-store`. Shared schemas live in `packages/contracts/src/auth/auth.schema.ts`. Unsafe browser requests require an exact trusted `Origin`; authenticated mutations additionally require `X-CSRF-Token` from login/current-session responses. Login is origin-protected and throttled before hashing.

| Method/path                        | Request                                       | Result / authority                                                                                                                                                                                                                         |
| ---------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| POST `/login`                      | email, password                               | Safe current user + CSRF token; opaque HttpOnly cookie. Temporary login is restricted.                                                                                                                                                     |
| GET `/me`                          | session cookie                                | Revalidated current staff/role/branch + CSRF token; restricted sessions may check their minimum session state.                                                                                                                             |
| POST `/first-login-password`       | currentPassword, newPassword, confirmPassword | Valid unexpired mandatory-change session only; rotate cookie/session and revoke all old sessions.                                                                                                                                          |
| POST `/change-password`            | same password fields                          | Normal active session only; verify current password, rotate session, revoke all old sessions.                                                                                                                                              |
| POST `/logout`                     | cookie + CSRF                                 | Revoke current valid session, append audit, clear cookie. Already invalid sessions can clear their cookie idempotently.                                                                                                                    |
| POST `/staff/:id/reset-credential` | validated target UUID + cookie/CSRF           | Current unrestricted Super Admin only; active existing target. Replace hash/24h controls, revoke every old target session, record event/audit atomically. Disclose the generated temporary password once after commit. No later retrieval. |

Unknown email, wrong password, inactive account and expired temporary credential all return the same unauthenticated `401 INVALID_CREDENTIALS` response. Authenticated expired temporary sessions can receive `TEMPORARY_PASSWORD_EXPIRED` for administrator guidance. Other stable codes include `SESSION_EXPIRED`, `PASSWORD_CHANGE_REQUIRED`, `CURRENT_PASSWORD_INCORRECT`, `CREDENTIALS_CHANGED`, `ACCOUNT_UNAVAILABLE`, `VALIDATION_ERROR`, `CSRF_REJECTED`, `ORIGIN_REJECTED`, `ACCESS_DENIED` and `RATE_LIMITED`; EN/UR resources localize them without relying on server English text. Transport validation is 400, incorrect current password 422, invalid session 401 and forbidden authority 403.

## Security and persistence

- Node >=24.7/<25 native asynchronous Argon2id: 64 MiB, three passes, one lane, random 16-byte salt and 32-byte result; bounded PHC-format verification. No new runtime dependency. This native API is available in the selected Node runtime; deployments must use the declared engine floor. [Node documentation](https://nodejs.org/download/release/v24.15.0/docs/api/crypto.html).
- User-approved password policy: minimum 15 Unicode code points, spaces/Unicode allowed, no mandatory character-type rules; existing bounded 200-code-unit transport limit. Confirmation and difference from the current password are validated server-side using shared schemas and current-hash verification. Passwords are not trimmed or silently normalized.
- Random 32-byte opaque session token in `hb_session`, HttpOnly, SameSite=Strict, host-only, path `/api/v1`, Secure in production. Only SHA-256 token hashes are persisted in `StaffSession`. CSRF is derived per session by HMAC, delivered in the protected DTO and verified against its stored hash with a constant-time comparison. Neither token is persisted in frontend storage.
- Database clock, 8-hour maximum idle deadline and immutable 24-hour absolute deadline; deny at/after either. Staff-row locking and rereads serialize login, change, reset and revocation. Existing database guards prevent resurrection/absolute extension. Forbidden action/branch requests do not refresh idle time.
- Current role/status/credential restriction and current single branch assignment are read on protected requests. Current assignment rows are held during transactional authorization. Supplied role/branch claims never grant access. All five identifiers match Prisma exactly: `SUPER_ADMIN`, `FINANCE_REVIEWER`, `CONTENT_EDITOR`, `BRANCH_LEAD`, `HR_LEAD`; no legacy-role mapping or enum rename was introduced.
- `StaffCredential`, `StaffSession`, `CredentialEvent`, `BranchLeadAssignment` and `AuditEvent` are real Prisma/PostgreSQL records. Credential changes, reset and logout use the existing caller-transaction `appendAudit` writer. Password/token values never enter audit payloads; audit failures roll back password/session effects.
- Exact trusted origins are configured with `AUTH_TRUSTED_ORIGINS`; production requires explicit HTTPS origins. No wildcard/CORS bypass, public password reset, social login, role selector, account registration or localStorage authentication token was added. Only the harmless language preference uses localStorage.
- Login/password/reset throttling defaults to 10 requests per IP per 15 minutes, in addition to the existing API limit. The limiter is process-local; shared multi-instance throttling/proxy/topology tuning remains deployment work. No production exposure or deployment acceptance is claimed.

## Developer B integration contract

`AuthService.withAuthorization(token, action, branchId, callback)` opens the authorization transaction and passes its Prisma transaction capability and fresh safe user to the domain callback. Put sensitive record retrieval, scope/state rechecks and mutation/audit in that same callback. For unsafe operations use `withMutationAuthorization(token, csrfHeader, action, branchId, callback)` plus `trustedOrigin(configuredOrigins)`; missing CSRF fails closed. Do not authorize writes from cached middleware/frontend DTOs or open another independent transaction for audit.

`authorization.ts` provides explicit action grants and deny-by-default role/branch checks. Super Admin does not inherit HR decisions, Finance approval or CMS publishing. A Branch Lead grant requires the current exact branch ID; domain services must still validate the target record belongs to it and enforce lifecycle/financial state. General unspecified team/status grants remain absent. `requirePermission` is a route-read adapter, not a substitute for transactional record-level checks in the consumer.

Future Users coordinators must lock target staff and invoke `revokeSessions(tx, staffId, databaseNow)` with status changes/audit in the same transaction; reactivation must never restore old sessions. Branch replacement must use the documented staff/assignment locking order and preserve DB-01 leadership constraints. Last-admin protection, actual staff-management/deactivation UI/endpoints and branch-assignment mutation services remain the Users/Branches milestone. Tests prove current-state denial and former-branch loss; they do not claim those future administration services exist.

Frontend pages are exported from `features/auth/index.ts`. `ProtectedRoute` performs fresh session validation per navigation before rendering protected children, including restricted-first-login gating and optional role affordances. Actual authorization remains server-side. `useAuth` uses TanStack Query, cancels/removes protected queries on logout, password change, invalidation and role/branch-scope changes. Future domain query keys must include current staff/branch scope. Use the existing central `apiRequest` / `ApiError`, shared Zod schemas, React Hook Form and existing i18next resources. There is no second router/client/store.

Shared frontend ownership exception explicitly authorized by the user: minimum staff routes, central request/mutation/error handling, authentication translations, persisted locale, Vite test proxy target and auth E2E wiring. Public pages, public/shared layouts, global styles and Developer B's Finance/CMS domain files were preserved. H-01/H-06/H-09 are provided locally for B review, not accepted/merged integration.
