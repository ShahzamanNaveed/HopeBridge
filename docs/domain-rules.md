# Domain rules

Source: user-supplied Milestone 0 brief and confirmed documentation update dated 2026-10-26. These are requirements/design decisions, not implemented business behaviour.

## Official Requirements

- Branch statuses: Forming, Active, Paused, Closed. **SA-005/SA-006 - DECIDED:** New branches start Forming and may initially have no lead. Only Super Admin changes lifecycle: Forming -> Active/Closed; Active -> Paused/Closed; Paused -> Active/Closed; Closed -> none. Activation requires an already assigned active eligible Branch Lead; assignment alone does not activate. Closed cannot reopen; preserve code/history. See [branch lifecycle](flows/super-admin/manage-branches.md).
- Track offline collections with a server-enforced seven-day edit lock. No online payment integration.
- Weekly reports support auto-draft, submit, return, resubmit, approve and lock. The previously recorded draft -> submit -> return -> resubmit -> approve -> lock sequence describes required actions, not an exhaustive transition graph.
- Approved report figures are immutable, including against subsequent source edits. Audit changes and report transitions; use atomic transactions for critical financial/report/audit writes.
- Head Office dashboard includes correct figures, monthly trends and unsent collections. CSV and PDF export are required; detailed scope is pending.
- Enforce five-role permissions and branch isolation on the server. English/Urdu RTL is required for public and internal interfaces.

## Confirmed HWF Decisions

Organisation and Head Office/branch structure: [project overview](../project-context/01-project-overview.md). Role responsibilities: [permissions](permissions.md).

- Each branch has a unique database ID and unique automatically generated city-based code. Prefixes map uniquely to cities; sequence numbers are per prefix and concurrency-safe. Examples: LHR-001/LHR-002, FSD-001/FSD-002, ISB-001. Codes are never reused, including after closure; changing city retains the original code. Names, cities and addresses are not global identifiers. Authorize access using branch IDs.
- Public Get Involved applications do not immediately create members. Initial successful HR Lead acceptance, creation of exactly one Active member and decision audit commit in the same database transaction; HR Lead may accept or decline applications. Reacceptance reactivates the existing linked member instead of creating another.
- **Member identification - DECIDED:** Branch codes (LHR-001, LHR-002, FSD-001), application references (APP-000001 is a proposed reference format) and Volunteer/Member IDs (LHR-V0001, LHR-V0002, FSD-V0001) are separate identifiers. Members retain a separate internal immutable database primary key and one current primary branch, without a staff login account.
- Generate Volunteer IDs only on initial successful HR acceptance from the selected operational branch's authoritative current city code, never applicant residence or unverified free text. All branches in a city share its member sequence; each city has an independent sequence. Examples illustrate formats, not guaranteed allocated numbers. IDs are globally unique, permanent and never reused or manually changed. Database uniqueness constraints and concurrency-safe sequence/counter allocation are mandatory; never use MAX(id) + 1.
- Transfer to another city preserves original Volunteer ID/prefix and internal primary key. Source Branch Lead requests; HR Lead approves/rejects; only approved transfer changes current primary branch, preserving historical branch attribution. BL-004 requires Active member and a different Active target, checked at request and again at HR approval; source scope/current branch must match. Consent and financial handling remain pending.
- Accepted reversal returns the application to Pending and keeps the linked member Inactive with the same ID/key/history. Reacceptance sets that same member Active with the same ID; no new member or city allocation. These changes and decision audit are atomic; no issued ID is released by reversal. See [authoritative HR identification workflow](flows/hr-lead/volunteer-identification.md).
- Validate applications in frontend and backend, with server-side rate limiting and duplicate checks. Different emails do not prove distinct identities; similar personal details may be flagged for HR review rather than automatically rejected. Do not collect CNIC publicly or use real personal data in samples/tests.
- Public navigation has no Login or Sign Up buttons. Staff use a separate portal route and administratively provisioned accounts. Keep current routes until an implementation task authorizes changes.
- Public and staff systems share a connected backend and PostgreSQL database. Programs, branches and events use database-backed information; content supports draft/publish. These integrations remain unimplemented.

## FIN-010 to FIN-013 ? approved HWF financial decisions

These are DECIDED HWF business policies, not independently verified handbook wording or implemented capabilities. The supplied handbook constraint allows exact integer paisa or NUMERIC; HWF selects the model below. Official fixtures/expected totals remain unavailable and the financial gate NOT VERIFIED.

- **FIN-010 - DECIDED:** Currency PKR only; PostgreSQL `NUMERIC(18,2)` and Prisma `Decimal` with explicit precision/scale. Monetary API inputs/outputs are decimal strings with at most two fractional digits; direct records with excess precision are rejected, never silently rounded. Reject NaN, Infinity, unsupported precision/range and floating-point-derived arithmetic; never use JavaScript `number` for money arithmetic. Use decimal-safe calculations/comparisons and explicit `HALF_UP` only when calculation genuinely requires rounding. Positive collection/remittance amounts are distinct from signed adjustments. Apply the same exact model to aggregates, snapshots, dashboards and exports; no exchange-rate/multi-currency functionality.
- **FIN-011 - DECIDED:** An Approved correction may reduce recognized net after confirmed remittance. Preserve locked originals, confirmed remittances, Approved snapshots and adjustment history; retain original occurrence-week and later recognition-week attribution. Negative signed outstanding is an explicit reconciliation deficit, not permission to rewrite history. Expose it to authorized Finance/Head Office users, prevent remittance without sufficient available balance and require audited reconciliation. No automatic compensating payment, refund or deficit write-off; exact clearing/external recovery and cross-period settlement remain PENDING.
- **FIN-012 - DECIDED:** Assigned source Branch Lead may request cancellation of their Pending/awaiting-confirmation remittance, never finalize it or directly cancel Confirmed. Finance Reviewer alone approves/rejects a valid scoped Pending cancellation. Request leaves reservation intact; approval atomically marks remittance non-reserving Cancelled, releases its reservation exactly once and appends audit. Rejection retains original Pending remittance/reservation. Confirmation versus approved cancellation must serialize to one valid outcome: confirmed cannot cancel, cancelled cannot confirm; no negative/double releases or erased history. Exact status vocabulary/transition design is not a prescribed schema. Confirmed disputes, settlement authority/accounting and external bank evidence validation remain PENDING; no confirmed-remittance reversal endpoint.
- **FIN-013 - DECIDED:** Multiple sequential original-linked adjustment requests are allowed, with at most one PendingReview per original at any time. Source Branch Lead requests and Finance Reviewer approves/rejects each; closing one permits the next. Each has an immutable unique reference, request/decision/audit history; preserve original and all prior approvals. Only Approved adjustments are recognized, each exactly once in its eligible period; Rejected has zero effect. Transactionally recheck original amount plus all Approved signed adjustments, including Approved awaiting recognition, plus candidate: corrected collection value must not become negative. This per-collection limit differs from potentially negative branch signedOutstanding. Attachment technical configuration, external correction/recovery and exceptional dispute restrictions remain PENDING; FIN-018 reason/optional-file policy is DECIDED.

### FIN-011 logical measures

Use identical accounting scope, branch filters and recognition timing for each measure; these logical names do not prescribe database fields or replace unavailable official KPI/fixture interpretation.

- `netRecognizedCollections`: original recognized collection effects, including eligible Late Entry once instead of duplicate original recognition, plus Approved signed adjustments actually recognized in the scope. Approved awaiting recognition is not yet a recognized total.
- `confirmedRemittances`: confirmed amounts in the same scope.
- `signedOutstanding = netRecognizedCollections - confirmedRemittances`; may be negative.
- `reconciliationDeficit = max(0, -signedOutstanding)`.
- `availableToRemit = max(0, signedOutstanding - pendingReservedRemittances)` using committed active Pending reservations in scope. Account for the deficit through signedOutstanding; never deduct it again or clamp outstanding itself. Insufficient coverage blocks further remittance/confirmation; a deficit never silently cancels pending claims.

Illustrative FIN-013 example, not official fixture data: original PKR 10,000, Approved adjustments -500 then -300 yield corrected value 9,200; another -9,201 must fail. Do not interpret one PendingReview as one lifetime adjustment.
