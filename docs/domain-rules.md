# Domain rules

Source: user-supplied Milestone 0 brief and confirmed documentation update dated 2026-10-26. These are requirements/design decisions, not implemented business behaviour.

## Official Requirements

- Branch statuses: Forming, Active, Paused, Closed. Exact allowed transitions are pending.
- Track offline collections with a server-enforced seven-day edit lock. No online payment integration.
- Weekly reports support auto-draft, submit, return, resubmit, approve and lock. The previously recorded draft -> submit -> return -> resubmit -> approve -> lock sequence describes required actions, not an exhaustive transition graph.
- Approved report figures are immutable, including against subsequent source edits. Audit changes and report transitions; use atomic transactions for critical financial/report/audit writes.
- Head Office dashboard includes correct figures, monthly trends and unsent collections. CSV and PDF export are required; detailed scope is pending.
- Enforce five-role permissions and branch isolation on the server. English/Urdu RTL is required for public and internal interfaces.

## Confirmed HWF Decisions

Organisation and Head Office/branch structure: [project overview](../project-context/01-project-overview.md). Role responsibilities: [permissions](permissions.md).

- Each branch has a unique database ID and unique automatically generated city-based code. Prefixes map uniquely to cities; sequence numbers are per prefix and concurrency-safe. Examples: LHR-001/LHR-002, FSD-001/FSD-002, ISB-001. Codes are never reused, including after closure; changing city retains the original code. Names, cities and addresses are not global identifiers. Authorize access using branch IDs.
- Public Get Involved applications do not immediately create members. Initial successful HR Lead acceptance, creation of exactly one Active member and decision audit commit in the same database transaction; HR Lead may accept or decline applications. Reacceptance reactivates the existing linked member instead of creating another.
- **Member identification - DECIDED:** Branch codes (LHR-001, LHR-002, FSD-001), application references (APP-000001 is a proposed reference format) and Volunteer/Member IDs (LHR-V0001, LHR-V0002, FSD-V0001) are separate identifiers. Members retain a separate internal immutable database primary key and one current primary branch, without a staff login account.
- Generate Volunteer IDs only on initial successful HR acceptance from the selected operational branch's authoritative current city code, never applicant residence or unverified free text. All branches in a city share its member sequence; each city has an independent sequence. Examples illustrate formats, not guaranteed allocated numbers. IDs are globally unique, permanent and never reused or manually changed. Database uniqueness constraints and concurrency-safe sequence/counter allocation are mandatory; never use MAX(id) + 1.
- Transfer to another city preserves original Volunteer ID/prefix and internal primary key. Source Branch Lead requests; HR Lead approves/rejects; only approved transfer changes current primary branch, preserving historical branch attribution. BL-004 requires Active member and a different Active target, checked at request and again at HR approval; source scope/current branch must match. Consent and financial handling remain pending.
- Accepted reversal returns the application to Pending and keeps the linked member Inactive with the same ID/key/history. Reacceptance sets that same member Active with the same ID; no new member or city allocation. These changes and decision audit are atomic; no issued ID is released by reversal. See [authoritative HR identification workflow](flows/hr-lead/volunteer-identification.md).
- Validate applications in frontend and backend, with server-side rate limiting and duplicate checks. Different emails do not prove distinct identities; similar personal details may be flagged for HR review rather than automatically rejected. Do not require CNIC publicly or use real personal data in samples/tests.
- Public navigation has no Login or Sign Up buttons. Staff use a separate portal route and administratively provisioned accounts. Keep current routes until an implementation task authorizes changes.
- Public and staff systems share a connected backend and PostgreSQL database. Programs, branches and events use database-backed information; content supports draft/publish. These integrations remain unimplemented.


- **BL-001 - DECIDED:** Normal collection edit cutoff is backend/database created_at + 7 x 24 hours, compared against authoritative UTC now; strictly before cutoff only. Edits, imports/backdated occurrence and frontend clocks never reset/extend it; exactly seven days fails.
- **BL-002 - DECIDED:** Own-branch authorization, age, report/snapshot permissions and integrity all required. Draft/Returned allow only in-window edits; Submitted locks until formal Return, Approved/Locked/finalized or approved snapshot inclusion permanently locks. No link is mandatory at creation; unlinked edits still check age/scope/immutability. Return never resets age; audit old/new values and eligible aggregate changes atomically. Expired-error correction uses FIN-002 separate next-report adjustment; FIN-006 source Branch Lead request/Finance decision governs recognition; no normal-edit override.
- **BL-003 - DECIDED:** One canonical report per branch/week, Asia/Karachi Monday 00:00 inclusive to next Monday 00:00 exclusive; exact money, no float. Example 2026-10-26 00:00 to exclusive 2026-11-02 00:00 PKT. FIN-001 attributes by actual occurrence time, not created_at; FIN-005 next-eligible-report late-entry recognition applies when original week is locked; this calendar is not the elapsed edit window.
- **BL-004 - DECIDED:** Source-scoped Branch Lead requests, HR alone approves/rejects transfer. Member and different target branch must be Active at request and rechecked at approval, including current source ownership/freshness. No identity regeneration or historical attribution change; target consent/open financial handling and source-Active-at-approval policy remain PENDING.
- **BL-005 - DECIDED:** Any authorized Active-to-Inactive member change ends all current active team assignments with end metadata and member/assignment audit in the same transaction; failure rolls everything back. Keep assignments/start dates/history, ID/branch, collections/reports/amounts intact. Inactive forbids new work. Reacceptance never reopens ended assignments; new assignments need explicit authorized Branch Lead action. No broad deactivation grant is implied.


- **FIN-001 - DECIDED:** Actual occurrence time selects original PKT Monday-to-next-Monday week, not created_at; created_at controls BL-001 edit cutoff and updated_at modification. Validate dates; backdating limits/evidence PENDING. FIN-005 handles already-Approved occurrence weeks without changing historical attribution.
- **FIN-002 - DECIDED:** Expired originals keep ID, amount, occurrence/creation timestamps and audit unchanged. Correction is a separate signed original-linked next-eligible-report adjustment; gross/adjustment effects exact and separately explainable, never double-counted. FIN-006 defines Branch Lead request and Finance approval before recognition; evidence, sequential corrections and remitted-cash effects remain PENDING.
- **FIN-003 - DECIDED:** Own-branch Branch Lead records remittance awaiting independent Finance confirmation; confirmation actor/time/state, audit and confirmed-outstanding updates atomic and once only. Unconfirmed is not settled. FIN-007 defines partial remittances/reservations and FIN-009 required details; no payment/bank integration.
- **FIN-004 - DECIDED:** Canonical states Draft, Submitted, Returned, Approved; Approved means permanently Locked with locked_at/equivalent metadata. Finance Reviewer approval, snapshot, reviewer/time and approval-lock audit are one protected transaction. No manual final lock or Approved/editable state. Resubmit uses Submitted with new revision/event; preserve Return feedback and immutable snapshots. Concurrency/transaction failure must not partially approve or duplicate events.


- **FIN-005 - DECIDED:** Preserve actual occurrence and original week when entered after that report is Approved/Locked; recognize one distinct audited Late Entry line referencing original collection/week in earliest subsequent same-branch report eligible for new lines. Never insert into Submitted or Approved. If none exists, persist awaiting inclusion. One original and at most one active recognition line; never also recognize in original week or cumulative totals twice, nor create an automatic negative adjustment. Transactional/idempotent allocation and uniqueness guard entry/report-generation/approval races.

- **FIN-006 - DECIDED:** Source-scoped Branch Lead requests expired or immutable-original correction with unique reference, original/branch link, signed exact amount, mandatory explanation, requester/time, applicable evidence reference, status and Finance metadata. States PendingReview -> Approved or Rejected, decision once by Finance Reviewer. Only Approved recognized once in next eligible report; persist Approved awaiting recognition if no report available. Rejected has zero effect/history retained. Recheck source, original eligibility, duplicate correction and balance integrity atomically with decision/audit/recognition. Submitted-only edit lock uses Return, not adjustment bypass. Evidence, sequential adjustment limits, Finance decision explanation and remitted-cash/negative-balance recovery remain PENDING.

- **FIN-007 - DECIDED:** Partial remittances allowed; over-remittance rejected at submission and confirmation using exact protected branch balances. Outstanding-not-yet-confirmed = recognized net collections minus Finance-confirmed remittances, subject to approved adjustment reconciliation. Available-to-remit = outstanding minus committed active pending reservations. Submission reserves, not confirms. Confirmation converts its own reservation to confirmed effect once, excluding self from other pending reservations; retain same claim, never require amount to fit available balance again after subtracting itself. Concurrent submissions/confirmations cannot over-reserve or double-settle. Cancellation/expiry/dispute/rejection/reservation-release rules remain PENDING; stuck reservation is a known edge case.

- **FIN-008 - DECIDED:** Finance return only from Submitted requires meaningful nonempty explanation after trimming; backend rejects blank/whitespace and preserves Submitted. Store reason with actor/time/report/from-to/revision and audit atomically. Branch Lead may read feedback; Approved cannot return and cutoff never resets. Return/approval race has one valid outcome.

- **FIN-009 - DECIDED:** Remittance requires positive exact amount, valid transfer date, trimmed nonempty transfer reference and source branch derived from authorized Branch Lead assignment. Evidence upload optional: absence alone cannot invalidate; supported uploads require backend type/size/access/malware controls. Reference is not receipt proof; independent Finance confirmation and audit still required. No new financial notification requirement.

Financial categories: original occurrence collections; separate Late Entry recognition (not another collection); Approved signed adjustments; pending reserved remittances; confirmed remittances; outstanding and available-to-remit. Recognized net counts each original or its Late Entry once plus Approved recognized adjustments once. Weekly recognition, occurrence views, cumulative dashboards and Head Office reconciliation may differ; preserve official KPI/fixture interpretation when supplied. Official financial gate NOT VERIFIED: handbook/fixtures unavailable. All mutations audit actor/role/time/action/reference, branch/report context, before/after and required reasons without sensitive credentials; preserve historical snapshots/audit.
