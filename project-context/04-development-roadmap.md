# Proposed 14-day roadmap

Day 1: repository foundation and verification. Day 2: handbook review, complete domain design, permission matrix, workflow specifications. Day 3: database migrations and shared contracts. Day 4: sessions, Argon2id authentication and CSRF. Day 5: authorization and branch scoping tests. Day 6: branch lifecycle. Day 7: volunteer applications and HR approvals. Day 8: member management. Day 9: offline collections and financial invariants. Day 10: weekly reporting and audited transitions. Day 11: sample-data dashboard reconciliation. Day 12: content draft/publish and public pages. Day 13: localization/accessibility, regression and security tests. Day 14: Render acceptance, CI evidence and handover.

This is a proposed sequence, not a completed schedule. Schema implements approved HWF policies and documented provisional ShipLens scope; already decided permissions are not awaiting blanket reapproval. Specific unresolved business paths remain gated; authoritative dashboard acceptance depends on missing official fixtures/handbook. Deployment preparation should begin early once hosting credentials are available.

## Authoritative allocation and dependency handoffs

The owner-approved A/B allocation is now [11-team-ownership.md](11-team-ownership.md), superseding the earlier tentative backend-versus-UI proposal. Profiles are assigned responsibilities, not personal identities; this setup selects no active session profile. [12-development-handoff.md](12-development-handoff.md) owns current per-module progress, next actions and the live dependency queue. Read it and verify source/Git evidence before starting; do not duplicate status here.

| Profile     | Responsibility summary (full allocation in ownership authority)                                                                                                                                           |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Developer A | Auth/users/security/RBAC, Super Admin/branches, applications/HR/member/team/transfer backend AND domain UI, shared audit, Prisma/migrations/backend routes/contracts index and CI/deployment coordination |
| Developer B | Collections/remittances/reports/Finance Reviewer/dashboard/exports backend AND UI, CMS, seven public pages/public application frontend, shared frontend/router/client/i18n/E2E                            |

Required dependency milestones, not completed work:

1. **Profile/ownership check:** Identify A/B explicitly; inspect branch/status/source/latest ledger and conflicting work. Use independent clones/worktrees/feature branches. No destructive Git or automatic commit/push/PR. A integrates consolidated ledger updates; B contributes branch-local proposals in the same ledger path.
2. **Schema and contracts review:** B supplies Finance/CMS model/constraint requirements; A is sole central Prisma/migration editor. Domain owners agree shared Zod request/response/errors/version semantics with consumers; A edits central contracts index. Single-editor coordination also applies to central backend routes/middleware and B's frontend router/client/layout/i18n.
3. **Shared protected foundation:** A provides one audit writer/transaction capability and auth/session/current-role/branch/CSRF policies with actual permission/revocation tests. B consumes them for protected financial/CMS endpoints, never builds a duplicate audit/auth service. Independent public presentation can proceed when requested without claiming live backend integration.
4. **Identity/public UI handoff:** A owns public branch/application backend and application Zod contract, HR/member identity/transfer services and A's feature screens. B owns public form UI and shared routing/layout integration after agreement on A's exported page components. Branch Lead member/team/transfer is A; collection/report/remittance is B. Legal/member/transfer gaps remain gated.
5. **Financial/content integration:** B owns exact Decimal accounting, recognition/remittance/report services and critical domain tests, plus CMS publication. A supplies reviewed central schema/auth/audit/branch/member contracts. Agree source/revision/locking/transaction contracts before integration; no independent client totals or invented official fixture values.
6. **Evidence and release:** Each domain owner executes appropriate unit/HTTP/real-PostgreSQL/permission/concurrency checks; B coordinates full bilingual/RTL/browser/export UX checks. A coordinates CI/infrastructure/deployment/acceptance with B's domain evidence. Obtain official handbook/fixtures for exact KPI/four-gate assertions, verify current CI/runtime/health/Render and submission artifacts; historical foundation CI is not release acceptance.

Current deliverable state, producer/consumer references and unresolved dependencies belong only in the ledger. Future ownership exceptions require explicit coordination and recorded surface/editor/scope/consumer review. The 14-day sequence above remains a proposal, not delivery evidence. Technical provider/library choices do not block all unrelated work; [business gates](../docs/requirements/clarifications.md) restrict only affected unapproved paths. No implementation, Git mutation or deployment is performed by this handover setup.
