# weekly-reports

Purpose: Audited weekly reporting lifecycle.

Requirements/responsibilities: implement this scope from the supplied brief with backend validation, server-enforced permissions and appropriate branch scoping. Do not infer undocumented rules.

Dependencies: collections financial projection/recognition ports, branches eligibility, authorization and shared audit.

Planned APIs/system behavior (proposed, no routes implemented): Scheduled generation/recovery, scoped report reads, submit, return, resubmit and Finance approval actions; final locking is automatic in approval, not a separate API/user action. Final paths and schemas await design approval.

Database relationships (initial DB-01 physical contract in docs/database.md): Report snapshots, source collections and transition history.

Official Requirements: Auto-draft, submit, return, resubmit, approve and lock. The recorded draft -> submit -> return -> resubmit -> approve -> lock sequence is not a complete transition graph. Approved report figures are immutable even after source edits. Audit every transition atomically; use transactions for critical changes.

Confirmed HWF Decisions: Branch Lead manages assigned branch weekly reports; Finance Reviewer approves/returns reports. WR-001 to WR-006 finalize the report behavior below; unlisted actions receive no implied grant.

BL-003 - DECIDED: Reporting timezone is `Asia/Karachi`; week starts Monday 00:00 inclusive and ends the following Monday 00:00 exclusive. Each branch has one canonical weekly report per period, protected against duplicate concurrent generation. Store precise interval boundaries and use the FIN-010 PKR NUMERIC(18,2)/Prisma Decimal model with decimal-string API values, never binary floating-point approximations.

Preserve Draft -> Submit -> Return -> Resubmit -> Approve -> Lock lifecycle actions, with FIN-004 applying approval and locking atomically. Resubmission may return to Submitted with a new revision/event; no extra permanent status is implied. Return is not mandatory before approval. Approved snapshots remain immutable, and every critical transition and its audit commit atomically.

FIN-001 - DECIDED: Actual occurrence time selects original PKT Monday-to-next-Monday week, not created_at; created_at controls BL-001 edit cutoff and updated_at modification. Validate dates; backdating limits/evidence PENDING. FIN-005 handles already-Approved occurrence weeks without changing historical attribution.

FIN-002 - DECIDED: Expired originals keep ID, amount, occurrence/creation timestamps and audit unchanged. Correction is a separate signed original-linked next-eligible-report adjustment; gross/adjustment effects exact and separately explainable, never double-counted. FIN-006 defines Branch Lead request and Finance approval before recognition; adjustment-upload technical configuration and external deficit-clearing/refund/recovery/period-settlement details remain PENDING; FIN-018 reason/optional-file policy is DECIDED; FIN-011/FIN-013 decide deficit accounting and sequential adjustment invariants.

FIN-003 - DECIDED: Own-branch Branch Lead records remittance awaiting independent Finance confirmation; confirmation actor/time/state, audit and confirmed-outstanding updates atomic and once only. Unconfirmed is not settled. FIN-007 defines partial remittances/reservations and FIN-009 required details; no payment/bank integration.

FIN-004 - DECIDED: Canonical report states Draft, Submitted, Returned, Approved. Approved means permanently Locked, with locked_at/equivalent metadata applied in the same protected Finance Reviewer approval transaction as authorized submitted revision, approver/time and approval-lock audit. No later manual final lock, independent permission or Approved/editable state. Preserve submitted/returned/resubmitted revision and feedback history; concurrent approval/return/edit cannot corrupt finalization.

FIN-005 - DECIDED: Preserve actual occurrence and original week when entered after that report is Approved/Locked; recognize one distinct audited Late Entry line referencing original collection/week in earliest subsequent same-branch report eligible for new lines. Never insert into Submitted or Approved. If none exists, persist awaiting inclusion. One original and at most one active recognition line; never also recognize in original week or cumulative totals twice, nor create an automatic negative adjustment. Transactional/idempotent allocation and uniqueness guard entry/report-generation/approval races.

FIN-006 - DECIDED: Source-scoped Branch Lead requests expired or immutable-original correction with unique reference, original/branch link, signed exact amount, mandatory explanation, requester/time, applicable evidence reference, status and Finance metadata. States PendingReview -> Approved or Rejected, decision once by Finance Reviewer. Only Approved recognized once in next eligible report; persist Approved awaiting recognition if no report available. Rejected has zero effect/history retained. Recheck source, original eligibility, duplicate correction and balance integrity atomically with decision/audit/recognition. Submitted-only edit lock uses Return, not adjustment bypass. FIN-013 permits sequential requests with at most one PendingReview and cumulative approved corrected value never negative. FIN-011 permits explicit signed deficits after remittance. Adjustment-upload technical configuration, Finance decision explanations and external deficit-clearing/refund/recovery/period-settlement details remain PENDING; FIN-018 reason mandatory/file optional is DECIDED.

FIN-007 - DECIDED: Partial remittances allowed; over-remittance rejected at submission and confirmation using exact protected branch balances. Outstanding-not-yet-confirmed = recognized net collections minus Finance-confirmed remittances, subject to approved adjustment reconciliation. FIN-011 availableToRemit = max(0, signedOutstanding minus committed active pending reservations); signedOutstanding may be negative and its deficit is exposed separately, never subtracted twice. Submission reserves, not confirms. Confirmation converts its own reservation to confirmed effect once, excluding self from other pending reservations; retain same claim, never require amount to fit available balance again after subtracting itself. Concurrent submissions/confirmations cannot over-reserve or double-settle. FIN-012 defines requested Pending-remittance cancellation and exactly-once release only on Finance approval. Expiry, other remittance rejection/release paths, confirmed disputes/settlement and external bank evidence validation remain PENDING.

FIN-008 - DECIDED: Finance return only from Submitted requires meaningful nonempty explanation after trimming; backend rejects blank/whitespace and preserves Submitted. Store reason with actor/time/report/from-to/revision and audit atomically. Branch Lead may read feedback; Approved cannot return and cutoff never resets. Return/approval race has one valid outcome.

FIN-009 - DECIDED: Remittance requires positive exact amount, valid transfer date, trimmed nonempty transfer reference and source branch derived from authorized Branch Lead assignment. Evidence upload optional: absence alone cannot invalidate; supported uploads require backend type/size/access/malware controls. Reference is not receipt proof; independent Finance confirmation and audit still required. No new financial notification requirement.

Financial categories: original occurrence collections; separate Late Entry recognition (not another collection); Approved signed adjustments; pending reserved remittances; confirmed remittances; outstanding and available-to-remit. Recognized net counts each original or its Late Entry once plus Approved recognized adjustments once. Weekly recognition, occurrence views, cumulative dashboards and Head Office reconciliation may differ; preserve official KPI/fixture interpretation when supplied. Official financial gate NOT VERIFIED: handbook/fixtures unavailable. All mutations audit actor/role/time/action/reference, branch/report context, before/after and required reasons without sensitive credentials; preserve historical snapshots/audit.

FIN-010 - DECIDED: PKR `NUMERIC(18,2)` / Prisma Decimal; decimal-string APIs, at most two fractional digits, reject excess input precision/nonfinite or float-derived money. No JavaScript number monetary arithmetic; decimal-safe comparisons/calculations, HALF_UP only where calculation requires rounding. Positive collection/remittance amounts and signed corrections remain distinct; same exact model for totals/snapshots/exports.

FIN-011 - DECIDED: netRecognizedCollections counts original-or-Late Entry once plus Approved recognized signed adjustments; confirmedRemittances uses same scope/timing. signedOutstanding = netRecognizedCollections - confirmedRemittances may be negative; reconciliationDeficit = max(0, -signedOutstanding). availableToRemit = max(0, signedOutstanding - active pending reservations), never deduct deficit twice. Expose deficits to authorized Finance/Head Office, preserve locked originals/confirmed remittances/Approved snapshots/adjustment history and occurrence/recognition attribution; no automatic payment/write-off. Further remittance requires sufficient coverage; external clearing/recovery/period settlement remains PENDING.

FIN-012 - DECIDED: Own-branch Branch Lead requests Pending remittance cancellation; only Finance approves/rejects. Request keeps reservation; approval atomically cancels to a non-reserving state, releases once and audits; rejection keeps Pending/reservation. Confirmation/cancellation race has one valid outcome; confirmed cannot cancel, cancelled cannot confirm, no negative/double release. No confirmed reversal/erasure grant.

FIN-013 - DECIDED: Multiple sequential requests, at most one PendingReview per original, each Finance-decided with unique immutable reference/request/decision/audit. Closing request permits next; only Approved recognized exactly once in eligible future report. Recheck original plus all Approved adjustments (including awaiting recognition) plus candidate >= zero in approval transaction. Rejected zero effect; preserve prior approvals/original. See [authoritative financial rules](../../docs/domain-rules.md).

## WR-001 to WR-006 - DECIDED operating behavior

- **WR-001 - DECIDED:** At completion of every Asia/Karachi Monday 00:00 inclusive to next Monday 00:00 exclusive week, authoritative application/database time triggers automatic Draft for just-completed week for eligible Active/Paused operational branches. Paused may retain financial obligations; generation never depends on dashboard access. Head Office is not operational; FIN-014 prohibits ordinary future-week Closed reports; exact legitimate pre-closure recognition container/period PENDING, never retroactively delete historical reports.
- **WR-002 - DECIDED:** Subsequent scheduled/recovery process detects missing eligible branch/week records after downtime/transient failure and creates safely. One canonical report per branch/week through unique database constraint and transactional concurrency protection; retries idempotent, never overwrite/reset existing Draft/Submitted/Returned/Approved. Auditable/observable recovery uses system attribution, not fake users/sixth role. Hosting technology remains an implementation choice; memory-only timer without recovery insufficient.
- **WR-003 - DECIDED:** Draft and Returned show latest legitimately eligible financial values: original occurrence week, correct later Late Entry/Approved signed adjustment recognition, original edit-window/report-state restrictions, exact PKR and own-branch scope. Each submit/resubmit transaction captures immutable consistent submission revision with submitter/time and freezes figures for Finance; Submitted locks included originals. Return preserves old revision and only permits original-age/state-valid corrections; resubmit creates new revision, retaining all earlier ones. Finance approval atomically locks immutable final snapshot; later adjustments/remittance confirmations/records do not rewrite it. Live calculations are not historical evidence.
- **WR-004 - DECIDED:** Finance approval transaction must recheck unresolved issues capable of materially changing this report's eligible figures. Map branch/report/recognition scope and distinguish original occurrence period, later recognition period and report under review; unrelated branch/period/non-affecting requests never automatically block. Unapproved adjustments never recognized. Denial leaves state unchanged; resolution requires reassessment. If figures need correction use authorized Return/resubmit, not mutation of frozen revision. Multi-period dependencies must be explicit; exact multi-period treatment needs implementation-level specification rather than blanket blocking. This policy does not add an automatic submission block.
- **WR-005 - DECIDED:** Eligible Active/Paused branch gets Draft even without new collections, Late Entry or Approved adjustments. Show correct zero activity amounts, no fabricated transactions; retain real carried financial context rather than assuming obligations vanish. Branch Lead may submit valid zero-activity report; Finance may Return/approve using normal reason/state/audit rules.
- **WR-006 - DECIDED:** Every generation/submit/Return/resubmit/approve-auto-lock action backend-checks state, version or equivalent atomic concurrency control, permission and branch/Finance separation. State/new revision or snapshot/append-only audit commit together; competing incompatible actions cannot both commit, repeated requests create no duplicate successful events/recognition. Safe conflict rejection/rollback leaves no partial state/audit. No Approved -> Draft/Returned and no later manual Lock.
